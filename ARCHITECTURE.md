# Architecture

How GitCanvas is put together, and why the boundaries fall where they do.
Written for whoever opens this repository next, including the author six months
from now.

## The shape

```
                 ┌──────────────────────────────────────┐
                 │  src/            React + TypeScript  │
                 │                                      │
                 │  components/  ← DOM, events, render  │
                 │  lib/graph-layout/  ← pure, no DOM   │
                 │  lib/ipc/     ← typed call wrappers  │
                 │  bindings.ts  ← GENERATED from Rust  │
                 └───────────────┬──────────────────────┘
                                 │  IPC, types generated by specta
                 ┌───────────────┴──────────────────────┐
                 │  src-tauri/      the IPC layer only  │
                 │  commands/  state.rs                 │
                 └───────────────┬──────────────────────┘
                                 │  plain Rust calls
                 ┌───────────────┴──────────────────────┐
                 │  crates/gitcanvas-core/              │
                 │  the git domain. No tauri dependency │
                 └──────────────────────────────────────┘
```

Dependencies point in one direction only. `gitcanvas-core` does not know the
application exists; `src-tauri` does not know the interface exists.

## Three boundaries, each enforced by a build failure

A rule that depends on someone remembering it is already technical debt. Each
of these is enforced by something that fails, and each was verified by
deliberately breaking it once.

### 1. The git domain cannot reach Tauri

`crates/gitcanvas-core` has no `tauri` dependency, so `use tauri::…` inside it
does not compile. That is the whole mechanism — no lint, no convention, no code
review step.

The payoff is testability: `cargo test -p gitcanvas-core` runs the entire git
engine without building an application or installing a single system webview
library, which is also why the `dev` CI job is fast.

### 2. The layout algorithm cannot reach the DOM

`src/lib/graph-layout/` is the most valuable code here and the easiest to break
without noticing. It stays a pure function of its input:

- ESLint forbids importing anything outside its own directory, plus React,
  `@tauri-apps/*`, and the DOM globals.
- Its tests run in vitest's `node` environment, where `window` does not exist.
- Its coverage threshold is 90%, higher than the rest of the project.

If something in there ever needs `document`, the responsibility is in the wrong
place and belongs in a component.

### 3. No type is written by hand on both sides

Every type crossing the IPC boundary is defined once, in Rust, and generated
into `src/bindings.ts` by `tauri-specta`. Writing the same type twice is the
number one source of silent bugs in Tauri applications: change a field in Rust,
forget TypeScript, and nothing complains until runtime.

Generation alone is not enough — a stale generated file lies just as
convincingly. So `cargo test` regenerates the file, and CI runs
`git diff --exit-code src/bindings.ts`. A drifted contract fails the build.

Application code imports from `lib/ipc/`, never from `bindings.ts` directly, so
a changed command signature breaks one file instead of every call site.

## Rules inside the Rust code

- **No `unwrap`, `expect`, `panic!` or raw indexing in production code.**
  Denied at the workspace level by clippy, with an opt-out in tests where a
  failing assertion is the point. A panic inside a command takes down the whole
  application.
- **Every failure is an `AppError`**, a single typed enum that serializes to
  TypeScript like any other contract.
- **Everything touching `git2` runs in `spawn_blocking`.** libgit2 is
  synchronous; without this a large repository freezes the interface.
- **State holds a validated path, never a live `git2::Repository`.**
  `Repository` is not safely shareable across threads, and forcing it behind a
  lock buys contention and bugs. Opening a repository is cheap — it reads refs,
  not history — so each command opens its own handle. An invalid path is
  unrepresentable rather than "validated somewhere".

## Why the layout lives in TypeScript

The graph layout could run in Rust. It runs in TypeScript because it is a
rendering concern: it decides which lane a commit occupies and how its lines
curve, which is a question about the picture, not about git. Keeping it next to
the renderer means one language for one concern, no IPC round trip per scroll,
and tests that run in milliseconds.

It is also resumable — `layout(commits, previousState)` — so loading the next
page of history continues the walk instead of recomputing it. Recomputing would
reshuffle the lanes of the commits already on screen, and the graph would jump
under the cursor.

## Where things run

| Concern | Lives in | Runs on |
|---|---|---|
| Reading git | `gitcanvas-core` | A blocking thread pool |
| IPC translation | `src-tauri/commands/` | Tauri's async runtime |
| Lane assignment | `lib/graph-layout/` | The renderer, synchronously |
| Drawing | `components/GraphCanvas/` | The webview |

## Verification

| When | What runs |
|---|---|
| Every commit | `cargo fmt`, ESLint, Prettier — about two seconds |
| Push to `dev` | Types, lint, frontend tests, git engine tests, on Linux |
| Pull request to `main` | The full matrix on three operating systems: clippy with `-D warnings`, all tests, coverage thresholds, the bindings drift check, and a real bundle build |
| Tag `v*.*.*` | Release notes from `CHANGELOG.md`, plus installers per platform |

The gate is the pull request into `main`, and nowhere else. `dev` stays fast on
purpose.
